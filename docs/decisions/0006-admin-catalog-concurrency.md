# ADR-0006: Версии каталога и атомарное административное редактирование

- Статус: Accepted — этап 05.2 и исправление согласования условий приняты пользователем после отдельной проверки
- Дата: 2026-08-31

## Контекст

Две открытые формы не должны молча затирать изменения друг друга. Назначения и порядок сохраняются целиком, включая перестановки при одинаковом displayOrder. Миллисекундный updatedAt не гарантирует уникальность последовательных изменений. Существующие записи, снимки услуги и защищённые ссылки сохраняют прежний смысл.

## Решение

- Prisma Migrate добавляет только Service.version и Master.version (INTEGER, default 0, CHECK >= 0). Это технические счётчики конкурентного редактирования. Они увеличиваются при каждом сохранении соответствующей сущности и при изменении её displayOrder. Услуга и мастер с версией из устаревшей формы получают CONFLICT до записи. Возврат полей к прежним значениям (ABA) не возвращает старую версию.
- Все административные записи каталога используют одну транзакционную PostgreSQL advisory lock (526008, 52) и ReadCommitted. После ожидания блокировки читается актуальная версия. Небольшая частота административных изменений позволяет обойтись одним замком, без Redis и универсального repository. Чтения не блокируются и используют RepeatableRead для согласованных списков услуг и назначений.
- Порядок при чтении — displayOrder, затем UUID. Отпечаток всего списка вычисляется SHA-256 от последовательности id/version/displayOrder. Команда «Выше/Ниже» предъявляет этот отпечаток и ID. После блокировки сервер заново сверяет его, меняет соседей и нормализует позиции в одной транзакции. Параллельное редактирование, перестановка или добавление строки делает старый отпечаток недействительным. Это консервативно: изменение названия тоже требует обновить список перед перестановкой.
- Все ID назначений проверяются до первой записи. Сохранение мастера, снятие отсутствующих и добавление новых назначений составляют одну транзакцию. Сохранившиеся связи не пересоздаются; деактивация сама по себе не удаляет связи. Поле photoMediaId и графики не принимаются из формы и не изменяются.
- Серверная граница проверяет существующую сессию 05.1 и активность администратора до операции, а для записи — ещё раз после ожидания замка. Для этого SQL-проверка getActiveAdmin вынесена из прежнего AuthService без изменения её условий. Авторизация не кешируется. Origin/Sec-Fetch-Site проверяются для каждой Action; схема входа строгая. GET не меняет данных.
- Административная транзакция не повторяется автоматически. Исключение, включая неизвестный исход COMMIT, даёт UNAVAILABLE. UI оставляет ввод, блокирует повторное сохранение и предлагает открыть актуальный список в новой вкладке. После проверки пользователь может открыть новую форму осознанно. Отдельного протокола идемпотентности административного создания нет; гарантировать exactly-once при ручном повторе нельзя.
- Успешный ответ содержит ID и согласованный снимок административного каталога из той же транзакции, без внутренних полей аккаунтов, медиа и записей. Навигация между разделами загружает полный документ с новым nonce. Публичный каталог динамический, без кеша; существующий booking повторно проверяет ограничения в Serializable-транзакции. Идемпотентность публичной записи, алгоритм «Любой мастер» и exclusion constraint не меняются.

## Последствия и пределы

Сериализация касается только административных изменений каталога, а не бронирования или чтения. Уже начавшаяся операция может завершиться до конкурирующего изменения: ранее выполненную запись или чтение отозвать нельзя. Следующая новая запись проверяет текущие ограничения; повтор прежней идемпотентной попытки возвращает её результат даже после деактивации.

Все будущие изменяющие каталог операции должны соблюдать этот протокол: блокировка, сверка версии и увеличение версии. Прямые SQL-изменения оператором в обход протокола не защищают открытые формы; для них необходим отдельный регламент. На переполнении INTEGER операция безопасно откатывается; автоматического сброса версии нет. Замок не является защитой от сетевого DoS; остаются ограничения тела Actions (16 КиБ) и требования к production proxy.

Технические пределы ввода: имя/название до 160 UTF-16 символов, описание до 2000, до 100 уникальных ID назначений за запрос. Цена и длительность ограничены положительным PostgreSQL INTEGER. Десятичная строка рублей с точкой или запятой преобразуется через BigInt и затем в безопасное целое число копеек; округления нет. Уникальность названий и кратность длительности 15 не вводятся.
