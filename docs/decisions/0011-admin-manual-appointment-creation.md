# ADR-0011: Идемпотентное ручное создание записи администратором

- Статус: Accepted
- Дата: 2026-09-01

## Контекст

Телефонная или офлайн-запись должна занимать интервал по тем же правилам, что и публичная, но создавать источник ADMIN и начальную историю от проверенного администратора. Публичный HTTP boundary нельзя вызывать из административной операции. Потерянный ответ после COMMIT не должен приводить к новой записи или потере защищённой ссылки, а отзыв сессии во время ожидания блокировок не должен раскрывать контакты или raw-токен.

Существующая схема уже содержит обязательный BookingRequest, AppointmentSource.ADMIN, MasterSelection, snapshots услуги, историю с changedByAdminId, hash клиентского токена и exclusion constraint. Новая таблица или миграция для 05.6 не требуется.

## Решение

Публичный BookingService и новый AdminBookingService используют общий внутренний транзакционный engine. Он не является HTTP boundary и не ослабляет различия внешних DTO. В общей части находятся:

1. вставка BookingRequest по idempotency key;
2. безопасный replay по request hash и constant-time сравнению raw-токена с сохранённым hash;
3. чтение активной услуги и проверка показанных service terms;
4. FOR SHARE настроек и проверка business context;
5. существующие selectAnyMaster/checkMasterInterval с утверждённым детерминированным выбором;
6. INSERT Appointment со снимками и только hash токена;
7. INSERT начальной истории в той же транзакции.

Публичный путь задаёт source=ONLINE и changedBy=CLIENT. Административный — source=ADMIN, changedBy=ADMIN и получает changedByAdminId только из действующей серверной сессии. TelegramLink и NotificationOutbox не создаются.

Административный DTO — отдельный strict Zod-контракт. Он требует UUID idempotencyKey, канонический 256-битный cancellation token, service terms hash, business context hash, SPECIFIC/ANY, локальную дату, начало с offset, существующую нормализацию российского телефона и literal confirmed=true. Цена, окончание, source, status, snapshots, history/admin ID и hashes извне не принимаются.

Fingerprint admin-booking-v1 — SHA-256 канонических исходных полей после Zod-нормализации: услуга, исходный выбор мастера, локальная дата, UTC-начало, имя, телефон, показанные service terms и business context. Секрет не входит в fingerprint: при replay он отдельно сверяется с cancellationTokenHash. Одинаковый ключ с изменённым payload, другим fingerprint или неправильным токеном возвращает IDEMPOTENCY_CONFLICT без токена и персональных данных.

Создание выполняется в Serializable-транзакции с существующим ограниченным retry только для ошибок сериализации/deadlock до известного результата транзакции. Автоматического повтора после неизвестного результата COMMIT в клиенте нет. Exclusion constraint остаётся окончательной защитой: предварительный scheduling check не заменяет её.

Активная административная сессия проверяется перед предметной работой и после значимых ожиданий. Финальная проверка в транзакции использует SELECT ... FOR SHARE строк сессии и администратора. Если их конкурентно изменили после снимка Serializable, PostgreSQL заставляет транзакцию повториться; повтор уже видит отзыв, истечение или отключение и откатывает BookingRequest, Appointment и историю. Успешная shared-блокировка удерживает доступ действующим до COMMIT. Boundary после транзакции ещё раз проверяет доступ и не выдаёт результат, контакты или токен при его потере.

Начальные данные формы и availability читаются в RepeatableRead с начальной авторизацией. Затем транзакция полностью завершается и освобождает соединение, после чего выполняется отдельная финальная авторизация. Это сохраняет исправление исчерпания пула 05.5: дополнительное соединение не запрашивается из callback открытой транзакции. До финальной проверки снимок остаётся локальным.

## Неизвестный результат и raw-токен

Пара idempotency key/cancellation token подготавливается отдельной изменяющей Server Action только после Origin и двойной проверки сессии. До первого create браузер обязан сохранить точный payload в sessionStorage текущей вкладки. localStorage и cookie не используются.

При неизвестном результате новая попытка блокируется. Разрешён только повтор того же сохранённого payload. Успешный replay возвращает исходную запись и тот же raw-токен. Контакты удаляются из sessionStorage через 30 минут; минимальный token marker остаётся для ручной сверки и блокировки новой попытки. Повреждённое хранилище также блокирует создание до осознанной сверки.

Raw-токен существует только в памяти/sessionStorage вкладки и в успешном Action DTO. В БД хранится SHA-256 hash. Абсолютная клиентская ссылка строится в браузере из window.location.origin и фиксированного /appointment#TOKEN; forwarded-заголовки не участвуют. Токен не попадает в query, pathname, server HTML, RSC-параметры или прикладные логи.

## UI и ошибки

Защищённый /admin/appointments/new использует четыре шага: услуга/мастер, локальная дата/время, контакты, итоговая проверка с реальным checkbox подтверждения. Изменение выбора, условий услуги или business context сбрасывает время и подтверждение. SLOT_UNAVAILABLE возвращает свежую доступность; контакты сохраняются. После успеха показываются снимок записи, plain-text подтверждение, отдельное копирование текста/ссылки и переход в карточку.

Clipboard API — только удобство. При отказе поле получает focus и полное выделение для ручного копирования. Текст удаляет управляющие символы и HTML-угловые скобки из полей; React не использует HTML-вставку.

## Последствия и ограничения

- Публичный и административный пути разделяют критическую транзакционную логику, но сохраняют строгие внешние границы.
- Согласованность зависит от штатных сервисов scheduling, протокола settings и PostgreSQL constraint; упрощённого второго расчёта нет.
- Успех, произошедший непосредственно перед отзывом после последней проверки, не может быть физически отменён boundary. Результат не выдаётся; сохранённая пара позволяет безопасно сверить/replay после нового входа.
- Уже показанные в открытой вкладке сведения удалённо не стираются.
- sessionStorage — вкладочный recovery, а не долговременное хранилище. После TTL контакты намеренно недоступны.
- Редактирование, перенос, Telegram, outbox, напоминания, медиа, deployment и 05.7 не входят в решение.
- Firefox/WebKit, физические устройства, screen reader, production HTTPS/reverse proxy и внешний аудит остаются отдельной независимой проверкой.
