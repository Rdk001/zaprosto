# ADR-0008: Атомарное управление расписанием и общий счётчик мастера

- Статус: Accepted — этап 05.3 принят пользователем после независимой проверки
- Дата: 2026-08-31

## Контекст

Нужны недельные рабочие часы, перерывы и исключения без потери параллельных изменений. Существуют модели WeeklyWorkInterval, WeeklyBreak, ScheduleException и ExceptionWorkInterval, уникальность (master_id, local_date), проверки порядка границ и Master.version из 05.2. Отдельный календарь визитов не входит в задание.

## Решение

1. Переиспользуем `Master.version` для всего расписания конкретного мастера. Сохранение недели, создание/изменение/удаление исключения сверяет предъявленную версию и увеличивает её ровно один раз в транзакции. Версия из устаревшей формы не заменяется актуальной автоматически. Удаление и повторное создание исключения не создаёт ABA: версия мастера монотонна. Отдельная версия недели или исключения и миграция не нужны.
2. Используем тот же advisory xact lock `(526008, 52)`, что каталог 05.2. Порядок: проверка текущей сессии → замок → повторная проверка сессии/активности → версия мастера → проверка входа и принадлежности → записи. Изменения используют ReadCommitted и не повторяются автоматически; чтения — RepeatableRead. В коде схема проверяется после авторизации и замка, до любых записей. Все связанные таблицы сохраняются атомарно. На переполнении INTEGER транзакция откатывается, сброс версии не производится.
3. Общая версия намеренно консервативна: изменение имени, назначений, активности или позиции мастера может вызвать конфликт редактора графика, а график — конфликт карточки и отпечатка порядка. Изменения разных мастеров не меняют версии друг друга. Глобальный замок сериализует короткие административные операции, но не публичное бронирование и не чтения; для текущего MVP это соответствует 05.2 и не требует новой инфраструктуры.
4. Создание исключения проверяет занятость даты и не использует upsert. Изменение/удаление проверяет ID **и** masterId; чужое исключение не изменяется. Уникальный индекс остаётся последней защитой даты. Смена типа и всех интервалов проходит в одной транзакции; DAY_OFF принимает только пустой набор интервалов. Ошибка БД после удаления старых интервалов откатывает также версию и дату/тип.
5. Все даты — строгие локальные календарные строки, часы — HH:mm без округления и сдвига. UTC-даты 1970-01-01 используются только как носитель PostgreSQL TIME. Даты исключений передаются в DATE через каноническую полночь UTC без преобразования зоны браузера. Предметный normalizeIntervals объединяет пересечения/дубли/соседние интервалы, не меняя объединения. Датированные границы проверяются существующим строгим Temporal-преобразованием **до нормализации**, чтобы объединение не скрывало ошибку DST. DAY_OFF не конвертирует неиспользуемое время; CUSTOM_HOURS сохраняет действие недельных перерывов.
6. Чтение исключений ограничено календарным месяцем и 31 строкой, мастеров — 50 на страницу по UUID с курсором. Для недельных и особых интервалов используются ограниченные выборки с одним дополнительным элементом для обнаружения превышения. Молча обрезанный график нельзя сохранить поверх полного. Сервер принимает максимум 16 интервалов одного типа на день, 7 разных дней, максимум 16 особых интервалов. Размер максимальной недели остаётся меньше 12 КиБ JSON при лимите Actions 16 КиБ. Контакты клиентов не входят в запросы и DTO.
7. Успешная Action возвращает новую версию и только изменённую часть графика из той же транзакции. UI не стирает черновик недели при сохранении исключения и наоборот. При конфликте или неизвестном результате COMMIT ввод остаётся в памяти страницы, повтор блокируется, доступна сверка в новой вкладке. Отдельной административной идемпотентности нет; ручной повтор допускается только после проверки актуальных данных в свежей форме.

## Публичная запись и пределы

Готовый scheduling, booking Serializable-транзакции, точная длительность, SPECIFIC/ANY, сетка начал 15 минут и PostgreSQL exclusion constraint не меняются. Чтения динамические; новый запрос после успешного сохранения видит актуальный график. Одновременно начавшиеся бронирование и изменение расписания могут завершиться в допустимом порядке: существующие записи не исправляются автоматически. Replay проверяется до расписания и возвращает прежнюю запись с теми же снимками и защищённой ссылкой. Согласование условий услуги сохраняет ADR-0007.

Недельные локальные часы нельзя проверить на все будущие DST-даты: при расчёте доступности остаются строгие правила этапа 03. Для конкретных дат CUSTOM_HOURS проверяет свои часы и действующие недельные перерывы. Если будущая смена недельных перерывов создаст проблемное DST-время, scheduling откажет без сдвига; администратор должен исправить границы либо закрыть день.

Прямые SQL-изменения вне протокола могут обойти проверку старых форм. Сессия, отозванная уже после последней проверки, не отменяет выполненную операцию; следующая граница откажет. Сетевой DoS, production proxy, MFA и прежний npm audit остаются отдельными вопросами.
