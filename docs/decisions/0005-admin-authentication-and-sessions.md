# ADR-0005: Аутентификация администратора и серверные сессии

- Статус: Accepted — результат 05.1 принят пользователем после отдельной проверки
- Дата: 2026-08-31

## Контекст

Этап 05.1 ограничен входом администратора и защищённым каркасом. AdminUser, AdminSession и PostgreSQL-счётчики уже существуют. Регистрация, новые роли, клиентские аккаунты и внешние провайдеры не нужны.

## Решение

- Используется `argon2@0.45.1` (node-argon2), привязка к реализации Argon2, с проверкой PHC средствами библиотеки. Argon2id: 65536 КиБ памяти, 3 прохода, parallelism=1, hashLength=32, случайная соль библиотеки. Это разумная нагрузка для редких административных входов и выше минимума [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Совместимость проверяется на Node.js 24 и в существующем образе node:24-bookworm-slim; требования и сборки описаны у [node-argon2](https://github.com/ranisalt/node-argon2).
- Логин: 3–64 ASCII-буквы/цифры и `._-`, приводится к нижнему регистру, без неявного trim. Пароль: 12–128 UTF-16 символов, не более 512 UTF-8 байт; пробелы сохраняются, правил обязательного набора символов нет. Оператору рекомендуется длинная уникальная фраза из менеджера паролей. Ограничения проверяются на сервере до Argon2. Лимит тела Server Actions остаётся 16 КиБ.
- Отсутствующий аккаунт проверяется по случайному dummy hash той же стоимости; неактивный и заблокированный — по своему hash до проверки состояния. Повреждённый hash проверяется через dummy и не раскрывает исключение. Dummy создаётся один раз на процесс, не сохраняется как пользователь. Ошибки неверного логина, пароля, неактивного аккаунта, блокировки и ограничения частоты имеют один публичный код/текст. Это не обещание строгого постоянного времени: БД, начальная генерация dummy и нагрузка могут влиять на задержку.
- Вход ограничивается существующим PostgreSQL limiter: отдельный namespace `adminLogin`, 10 попыток в минуту на клиента и 60 на установку, учитываются успешные и неуспешные валидные запросы. Атомарный UPSERT, время БД, насыщение счётчиков и существующая очистка истёкших строк обеспечивают работу между процессами и перезапусками. По умолчанию client bucket общий; правила доверия IP точно такие же, как в ADR-0004. Открытые IP и логины в таблицу лимитов не добавляются.
- После 5 неудачных проверок пароля AdminUser блокируется на 15 минут. Решения и счётчики сериализуются `SELECT FOR UPDATE`, время берётся из PostgreSQL после получения блокировки. Попытки во время блокировки не продлевают её и не увеличивают счётчик. После истечения следующая ошибка начинает новый счётчик, успех обнуляет его. Успешная проверка hash вне транзакции подтверждается повторным чтением hash под блокировкой, чтобы конкурирующий сброс не создавал сессию со старым паролем.
- Каждый успех создаёт новый криптографически случайный 256-битный непрозрачный токен. БД сохраняет только SHA-256 токена; публичный результат Action содержит только признак успеха и фиксированное внутреннее направление. Ранее выбранный клиентом session ID не принимается. Несколько независимых сессий допустимы; срок каждой — 12 часов без продления, чтобы охватить рабочую смену и ограничить срок украденного токена.
- При каждом чтении закрытых данных единый SQL-запрос проверяет hash, срок, отсутствие отзыва и активность AdminUser. Кеширования результата нет. Страница использует эту серверную границу; layout/proxy не считаются авторизацией. Будущие административные операции обязаны проверять сеанс в собственной серверной границе и возвращать только необходимые DTO.
- Вход/выход — Server Actions. Явная проверка точного Origin по PUBLIC_ORIGIN и Sec-Fetch-Site сохраняет ADR-0004 и дополняет встроенную защиту Next.js. Host, X-Forwarded-Host/Proto не определяют разрешённый источник или cookie policy. GET никогда не выполняет вход/выход. Выход идемпотентно отзывает только предъявленный токен; анонимному/истёкшему сеансу можно безопасно удалить cookie, закрытые данные не возвращаются. При сбое БД успешный выход не подтверждается и cookie не удаляется.
- HTTPS cookie: `__Host-zaprosto-admin`, HttpOnly, Secure, SameSite=Lax, Path=/, без Domain, expires равен сроку в БД. Для локального HTTP на localhost/127.0.0.1/[::1] используется отдельное имя `zaprosto-admin-local`, без Secure. Другой HTTP-origin запрещён сервером даже при NODE_ENV=development; NODE_ENV=production не исключает локальную проверку production-сборки. Production для пользователей — только HTTPS.
- Переход после входа разрешён только на реализованную `/admin`; URL/query/fragment из параметров не принимаются. UI делает полную навигацию для новой nonce-CSP. Административные страницы динамические и получают private/no-store, no-referrer, noindex, DENY и прежнюю CSP. Пароли, hashes и токены не попадают в props, ответы Actions, storage или прикладные логи.
- Создание первого администратора — только локальная TTY CLI. Пароль скрыт, подтверждается повторным вводом, аргументы/pipe запрещены. Повторное и параллельное создание не меняет существующие данные (транзакционная advisory lock). Отдельная ручная команда сброса меняет пароль и отзывает все сессии в одной транзакции. Активность аккаунта не меняет. Никаких setup/reset endpoints или seed-аккаунтов.

## Последствия и ограничения

Новая схема, миграция, Redis, OAuth, JWT и платные сервисы не требуются. Работающая БД нужна для каждого защищённого запроса; сбой закрывает доступ. Оставшиеся пустые/отозванные сессии удаляются оператором при необходимости, отдельный worker очистки для MVP не добавлен.

Глобальный предел может временно блокировать всех администраторов при атаке; лимит аккаунта тоже допускает отказ в обслуживании известного логина. Это осознанный компромисс MVP без сетевой инфраструктуры: необходимы ограничения трафика на proxy. Парольная авторизация без MFA не защищает от фишинга или компрометации компьютера. CSP и HttpOnly снижают риски, но не заменяют защиту от XSS. Отозвать уже выполненную операцию невозможно; последующие обращения проверяют актуальное состояние.
