# ADR-0007: Согласование показанных условий услуги при бронировании

- Статус: Accepted — этап 05.2 и исправление согласования условий приняты пользователем после отдельной проверки
- Дата: 2026-08-31

## Контекст

Клиент мог видеть 1500 ₽ / 35 минут, а после административного изменения сохранить запись за 2500 ₽ / 60 минут без нового согласия. Проверка доступности не обнаруживает изменение цены или названия; новая длительность тоже может помещаться в график. Service.version защищает административные формы, но ранее не связывала публичное подтверждение с показанными условиями.

## Решение

Публичный каталог возвращает termsHash: SHA-256 от JSON-массива фиксированного порядка `["service-terms-v1", id, name, priceKopecks, durationMinutes]`. Отпечаток вычисляется на сервере из тех же значений, которые возвращаются экрану. Он не секрет и не доказательство личности; клиент по-прежнему не задаёт цену или длительность записи. Изменение любого из трёх условий меняет отпечаток. Порядок, административная версия и несвязанные изменения его не меняют. Возврат к полностью тем же условиям допустим. Миграция и отдельный счётчик публичной версии не нужны; изменение SQL в обход увеличения Service.version тоже обнаруживается.

Новый create передаёт `expectedServiceTerms` показанной услуги (64 строчных hex-символа). UI фиксирует этот отпечаток вместе с исходным payload до первого запроса. Получение доступности или подготовка ключа попытки не заменяют его более свежим.

В Serializable-транзакции:

1. INSERT BookingRequest с уникальным ключом идемпотентности либо проверка replay.
2. Если запись уже есть, сверяются исходный requestHash и секрет. Возвращается та же запись с прежними снимками, даже если каталог изменился.
3. Для новой попытки читается активная услуга; expectedServiceTerms сравнивается с отпечатком в том же снимке БД.
4. Только совпадение разрешает scheduling и сохранение Appointment/истории со значениями из БД.

Отсутствие или несовпадение отпечатка вызывает исключение и откат всей транзакции, включая BookingRequest. Затем новая RepeatableRead-транзакция читает актуальные условия и доступность. Возвращается `SERVICE_TERMS_CHANGED { service: { id, name, priceKopecks, durationMinutes, termsHash }, availability }`. Если услуга уже исчезла или деактивирована, действует прежний REQUEST_REJECTED. Неподходящий мастер/дата могут дать пустую availability с причиной. Ошибка чтения после отката остаётся UNAVAILABLE на публичной границе; браузер сохраняет исходную попытку до достоверного ответа.

UI после подтверждённого отказа обновляет показанные название, цену и длительность, сбрасывает выбранное время, заново запрашивает доступность и сохраняет контакты. Клиент выбирает окно, просматривает условия и нажимает «Подтвердить обновлённые условия». Только тогда создаётся новая пара. Автоматической отправки или подстановки свежего отпечатка под старое подтверждение нет. Следующее изменение услуги снова проверяется в транзакции.

## Совместимость и восстановление

- Запрос с expectedServiceTerms использует requestHash от массива `booking-v2`: прежние поля booking-v1 в прежнем порядке, затем expectedServiceTerms. Хеш хранит исходные условия, а не пересчитывается из актуального каталога.
- Без поля сохраняется **точный прежний** алгоритм booking-v1. Это нужно только для replay существующих попыток; новая запись без поля всегда получает отказ с предложением согласовать актуальные условия.
- Старые requestHash, снимки Appointment, история и hashes защищённых ссылок не переписываются. Строки с NULL requestHash по-прежнему возвращают IDEMPOTENCY_CONFLICT.
- Ключ sessionStorage остаётся zaprosto.booking.v1. Старый pending без expectedServiceTerms читается и повторяется буквально, без обогащения свежим каталогом. Если прежний COMMIT состоялся, replay возвращает его результат. Если строки нет, подтверждённый отказ разрешает новое согласование.
- Удаление поля у уже созданной попытки booking-v2 не делает её старой совместимой попыткой: hash не совпадёт, исход остаётся неизвестным, новая запись заблокирована. Повреждённое хранилище сохраняет прежний blocker.
- Потеря ответа, RATE_LIMITED, FORBIDDEN, UNAVAILABLE и IDEMPOTENCY_CONFLICT не разрешают автоматическую новую попытку. TTL, защищённые ссылки и правила отмены не меняются.

## Проверки

Независимые `tests/integration/booking-terms.test.ts` и `tests/e2e/booking-terms.spec.ts` покрывают цену, длительность при свободном новом интервале, название, повторное согласие, отсутствие частичных строк, потерю успешного ответа с изменением каталога и replay, старый формат и неполные/подменённые запросы. Integration также проверяет ANY, недоступную новую длительность, повторное изменение условий и изменение только административного порядка. Браузерные сценарии используют настоящие Server Actions и отдельную PostgreSQL-БД; ответы создания не подменяются успешными заглушками.

## Пределы

Согласие относится к условиям услуги; доступность и активность по-прежнему перепроверяются сервером. Одновременное редактирование и бронирование могут сериализоваться в любом допустимом порядке, но сохранённые условия должны совпадать с предъявленным отпечатком и транзакционным снимком. Механизм не добавляет оплату, удержание слота, перенос или уведомления.
