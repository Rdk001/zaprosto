# ADR-0014: Архитектура Telegram-подключений и надёжного outbox

- Статус: Proposed
- Дата: 2026-09-04

## Контекст

Целевой MVP должен отправлять Telegram-уведомления, не нарушая основную операцию записи и не требуя платного сервиса. В принятой архитектуре уже есть отдельная роль процесса `worker`, общая PostgreSQL и ранние, пока не используемые модели `TelegramLink`, `NotificationOutbox`, `NotificationType` и `NotificationStatus`.

Ранняя `TelegramLink` смешивает одноразовый credential и долговременную связь, не описывает отключение и повторное подключение и не подходит для администратора. Ранняя `NotificationOutbox` не имеет получателя, lease, времени следующей попытки, terminal-состояний для неактуальной job и версии payload. Сохранять эти формы только ради отсутствия миграции нельзя.

Официальная документация Telegram задаёт следующие границы:

- [`getUpdates` и webhook взаимоисключающие](https://core.telegram.org/bots/api#getupdates); update подтверждается следующим `offset`, а offset нужно пересчитывать после ответа;
- Telegram [хранит непринятые updates не более 24 часов](https://core.telegram.org/bots/api#getting-updates);
- [`getWebhookInfo`](https://core.telegram.org/bots/api#getwebhookinfo) показывает активный webhook, а [`deleteWebhook`](https://core.telegram.org/bots/api#deletewebhook) выполняет явный переход обратно к polling;
- deep-link имеет вид `https://t.me/<bot_username>?start=<parameter>`, а [`parameter` ограничен 64 base64url-символами](https://core.telegram.org/bots/features#deep-linking);
- [бот не может первым начать разговор с пользователем](https://core.telegram.org/bots#how-are-bots-different-from-users);
- [`sendMessage`](https://core.telegram.org/bots/api#sendmessage) принимает текст до 4096 символов;
- при flood control Telegram может вернуть [`retry_after`](https://core.telegram.org/bots/api#responseparameters), а бесплатная отправка имеет [ограничения на один chat и общий broadcast](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this).

## Решение

### 1. Получение команд

На бесплатном старте используется long polling через `getUpdates` в существующем `worker`. Публичный HTTPS endpoint и tunnel для локальной разработки не нужны. Webhook остаётся возможной будущей заменой, но не частью MVP.

Только один worker получает updates. Единственная основная гарантия последовательного polling — session-level PostgreSQL advisory lock на отдельном соединении с ключом `(526008, 61)`. Потеря соединения освобождает lock и отменяет текущий long poll. Остальные worker-процессы могут параллельно обрабатывать outbox, но не вызывают `getUpdates`; poller без лидерского lock является неподдерживаемым режимом.

Offset хранится в singleton-строке `TelegramBotState`. Перед `getUpdates` лидер запоминает запрошенный offset, а после ответа повторно подтверждает на том же session connection владение advisory lock. Затем он сортирует batch по возрастанию `update_id` и обрабатывает updates отдельно и последовательно. Перед каждым update сохранённый `nextUpdateId` должен совпадать с состоянием, ожидаемым лидером после его собственных commit; изменение singleton другим процессом или потеря connection/lock останавливают batch без дальнейших эффектов. `update_id < nextUpdateId` является уже обработанным повтором, а `update_id >= nextUpdateId` допустим: числовой gap сам по себе не является ошибкой. Связь, jobs, использование токена и переход `nextUpdateId = update_id + 1` фиксируются одной PostgreSQL-транзакцией. Если транзакция не завершилась, offset не двигается. Эти проверки не делают безопасной параллельную работу двух poller; exactly-once для локальных изменений заявляется только внутри single-leader последовательного протокола, но не для внешней отправки сообщения.

Перед polling лидер вызывает `getMe` и `getWebhookInfo`. Непустой `WebhookInfo.url` блокирует polling и оставляет безопасный диагностический код. Worker не удаляет webhook автоматически при каждом старте. Переход выполняется отдельным осознанным операторским действием через `deleteWebhook({ drop_pending_updates: false })` с последующей проверкой `getWebhookInfo`.

### 2. Одноразовые deep links

Оба вида deep link используют 32 криптографически случайных байта. Base64url без padding занимает 43 символа; с префиксом `c_` для записи или `a_` для администратора итоговая длина равна 45 символам и сохраняет 256 бит случайной энтропии при лимите Telegram в 64 символа.

В PostgreSQL хранится только контекстно разделённый SHA-256 hash полного параметра. Raw-токен:

- возвращается защищённой web-границе только в ответе на создание ссылки;
- показывается один раз;
- не попадает в БД, логи, метрики, exception, URL приложения или клиентский bundle;
- присутствует только в предназначенном Telegram deep link;
- имеет TTL 30 минут и используется один раз.

Потерянный ответ не восстанавливает raw-токен из БД: повторное защищённое действие отзывает прежний неиспользованный токен и выдаёт новый. Для одного target одновременно существует не более одного неиспользованного и неотозванного токена.

Worker принимает link-команды только из private chat, от обычного пользователя и в точной форме `/start <token>` либо `/start@<настроенный_бот> <token>`. Телефон, username и имя профиля Telegram не используются для поиска пользователя.

### 3. Подключение клиента

Клиентская связь относится к одной `Appointment`. Ссылка создаётся только после явного действия клиента на защищённой странице записи, авторизованной существующим cancellation token, только для будущей `SCHEDULED`-записи и только когда Telegram worker подтверждён как готовый.

Успешный `/start` атомарно:

1. проверяет TTL, назначение и одноразовость токена;
2. повторно проверяет `SCHEDULED` и `startsAt > clock_timestamp()`;
3. создаёт неизменяемую по получателю `AppointmentTelegramConnection`;
4. отмечает токен использованным;
5. создаёт job подтверждения подключения;
6. создаёт reminder job, только если до `startsAt` строго больше двух часов;
7. продвигает Telegram offset.

Подключение менее чем за два часа разрешено, но отдельное напоминание не создаётся. Отменённая, завершённая, уже прошедшая или уже связанная с другим Telegram запись не подключается. Повтор того же update ничего не создаёт. Повторное нажатие Start тем же chat на уже использованный токен является идемпотентным; другой chat получает одинаковый нейтральный отказ без сведений о записи или существующей связи.

Один Telegram chat может быть связан с несколькими разными записями: сущности клиента и глобальной связи по номеру телефона в MVP нет.

### 4. Подключение администратора

Для администратора используется отдельная `AdminTelegramConnection`, а не nullable-поля в `AdminUser`.

Авторизованный администратор создаёт одноразовую ссылку только для собственной учётной записи. Связь разрешена только с private chat. На одного `AdminUser` допускается одна активная связь, а один private chat не может одновременно принадлежать двум активным административным связям. Отключение помечает связь неактивной и инвалидирует её неотправленные jobs; новое подключение создаёт новую identity связи.

Отдельная модель:

- не смешивает парольную аутентификацию с внешним каналом доставки;
- поддерживает несколько административных учётных записей без мультифилиальности;
- позволяет отключать и перевыпускать связь без переназначения старых jobs на новый chat;
- сохраняет понятный `onDelete` и аудит жизненного цикла.

Ручной `chat_id` в `.env` не является продуктовым сценарием. Он допустим только в отдельном локальном диагностическом инструменте разработчика и не используется producer-ами.

### 5. Transactional outbox

Каждая job, вызванная изменением бизнес-состояния, вставляется в той же транзакции, что `Appointment` и, где применимо, `AppointmentStatusHistory`. Внешний HTTP-запрос Telegram никогда не выполняется внутри этой транзакции.

Producer создаёт отдельную job для каждой активной identity получателя. Dedupe key строится из бизнес-события, версии записи, типа и identity connection; случайный ID попытки в key не входит. Повтор BookingRequest, повтор Server Action или replay update не создаёт второе логическое уведомление.

Новая outbox-модель поддерживает:

- `PENDING`, `PROCESSING`, `SENT`, `DEAD`, `CANCELLED` и `SKIPPED`;
- раздельные `scheduledAt` и `nextAttemptAt`;
- atomic claim через `FOR UPDATE SKIP LOCKED`;
- lease с fencing token, владельцем и сроком;
- восстановление зависшего `PROCESSING`;
- число попыток, `sentAt`, terminal `finishedAt`;
- безопасные `lastErrorCode` и `invalidationCode` без ответов Telegram;
- явную версию и ограниченный размер JSON payload;
- immutable recipient identity и уникальный `dedupeKey`.

Claim выполняется и коммитится до чтения `Appointment` и до сети. Worker не удерживает outbox lock, Appointment lock или транзакцию во время `sendMessage`.

### 6. Payload и формирование сообщений

Выбран гибрид:

- уведомления о конкретном создании, отмене или переносе используют snapshot события из payload;
- изменение записи хранит снимки «до» и «после», поэтому позднейшее изменение не переписывает смысл сообщения;
- подтверждение подключения и reminder формируются из актуальной `Appointment` непосредственно перед отправкой;
- reminder дополнительно сравнивает сохранённую identity визита с актуальными status, connection, service/master и временем.

Payload не содержит телефон, cancellation token/hash, Telegram link token/hash, session data, Bot Token, raw Telegram response или полный текст ошибки. В MVP телефон также не отправляется в Telegram: административное сообщение ведёт в защищённую карточку. Имя клиента при необходимости читается из актуальной Appointment и не дублируется в payload.

Сообщения отправляются простым текстом без `parse_mode`. Это исключает HTML/Markdown injection и ненужное экранирование; пользовательские строки всё равно проходят ограничение длины и удаление запрещённых control-символов.

### 7. Напоминания

Reminder назначается ровно на `startsAt - 2 часа`. Он создаётся только при активной клиентской connection и только если на момент создания job до визита строго больше двух часов.

Перенос в своей бизнес-транзакции инвалидирует старый reminder и при соблюдении правила создаёт новый. Отмена, `COMPLETED`, `NO_SHOW` или отключение connection также инвалидируют неотправленный reminder.

Непосредственно перед отправкой worker проверяет:

- `status = SCHEDULED`;
- актуальную connection identity;
- совпадение `startsAt`, `endsAt`, service/master и snapshot условий с identity reminder;
- отсутствие invalidation;
- наступление `scheduledAt`;
- непросроченный deadline.

Допустимое опоздание worker — 15 минут. После `scheduledAt + 15 минут` reminder получает `SKIPPED`; старое сообщение после длительного простоя не отправляется. Повторы также не выходят за этот deadline.

### 8. Семантика доставки и ошибки

Для `sendMessage` выбрана **at-least-once доставка с редкой возможностью дубля**. Telegram не принимает наш idempotency key и не участвует в транзакции PostgreSQL. Если worker упал после фактической отправки, но до `SENT`, либо потерял ответ, lease-восстановление повторит job. Exactly-once не заявляется.

Одна job имеет не более шести delivery claims; claim консервативно учитывается до сети. После обычной временной ошибки используется exponential backoff от 30 секунд до 15 минут с jitter 50–100% от расчётной задержки. `429` использует валидный положительный `retry_after` плюс небольшой jitter; значение до 24 часов соблюдается точно, отсутствующее/невалидное использует обычный backoff, а большее не сокращается до раннего повтора — job завершается безопасным terminal-кодом. Reminder ограничен собственным более ранним deadline.

При нескольких dispatcher процессах лимит не может быть process-local. Sender сначала берёт session advisory lock конкретного chat, затем общий lock бота. Общий lock удерживается до истечения 40 мс от фактического старта текущего HTTP-вызова, поэтому следующий worker физически не может начать раньше и общий предел составляет 25 стартов/с. Chat lock удерживается до завершения HTTP и не менее секунды от его старта. Locks живут на выделенных соединениях, но ни SQL-, ни бизнес-транзакция во время HTTP не удерживается.

Сетевые ошибки, неизвестный результат и Telegram `5xx` повторяются. Известные `bot blocked`, `chat not found`, `chat write forbidden` и `TELEGRAM_USER_DEACTIVATED` являются постоянными, завершают job и отключают соответствующую connection. Локальный неактивный администратор обрабатывается до сети отдельной причиной `ADMIN_USER_DEACTIVATED`. Ошибка запроса завершает только job. Ошибка конфигурации, неверный Bot Token, несовпадение bot identity или активный webhook переводят Telegram-подсистему в degraded mode, но не отключают пользовательские связи и не создают crash loop.

Официальный Bot API возвращает `error_code`, human-readable `description` и иногда `parameters`, но не обещает стабильный машинный контракт текста ошибки. Поэтому adapter преобразует ответы в ограниченный внутренний набор кодов и никогда не сохраняет полный `description`.

### 9. Конфигурация и безопасная деградация

В production используются:

- `TELEGRAM_BOT_TOKEN` — только в окружении worker;
- `TELEGRAM_BOT_USERNAME` — безопасное имя для web и worker;
- необязательный `TELEGRAM_POLL_TIMEOUT_SECONDS`, по умолчанию 30.

Limit polling, HTTP timeouts, batch size, lease, retry и reminder grace остаются проверенными константами, а не множеством environment variables. `TELEGRAM_BOT_USERNAME` сверяется с `getMe`; Bot Token не хранится в PostgreSQL и не передаётся web-процессу.

Ротация token того же `getMe.id` сохраняет offset и connections. Другая bot identity останавливает подсистему до явной операторской замены: прежние связи отключаются, их jobs и токены инвалидируются, offset сбрасывается, после чего пользователи подключаются заново.

Если Telegram не настроен или не готов, web и бронирование продолжают работать, producer-ы не делают внешних вызовов, новые кнопки подключения скрыты, worker остаётся жив и выдаёт только безопасный диагностический код.

## Рассмотренные альтернативы

### Webhook

Webhook уменьшает задержку и снимает long-poll соединение, но требует публичного HTTPS endpoint, настройки маршрутизации и защиты входящего endpoint. Для одного барбершопа это не даёт достаточной пользы на бесплатном старте. Переход в будущем возможен без изменения token, connection и outbox моделей.

### Автоматический поиск по телефону

Отклонён. Bot API не предоставляет безопасного соответствия номера записи Telegram-пользователю, а бот не может первым начать private conversation.

### `chat_id` администратора в `.env`

Отклонён как основной сценарий: нет доказательства владения chat, жизненного цикла, отключения, поддержки нескольких администраторов и безопасного перевыпуска.

### Telegram-поля в `AdminUser`

Отклонены из-за смешения auth и delivery, отсутствия отдельной identity connection и риска отправить старую job в новый chat после перепривязки.

### Отправка внутри бизнес-транзакции

Отклонена: внешний timeout удерживал бы PostgreSQL locks, а rollback не может отменить уже отправленное сообщение.

### Только актуальная Appointment при отправке

Отклонена для событий изменения: сообщение о конкретном переносе могло бы описать более позднее состояние. Полный snapshot для всех сообщений тоже отклонён, потому что дублировал бы лишние персональные данные и мешал server-side preflight reminder.

### Прекращение повторов после неизвестного результата

Отклонено в пользу at-least-once: для записи и отмены редкий дубль менее опасен, чем молчаливая потеря уведомления. Риск дубля показывается как ограничение, а не скрывается заявлением exactly-once.

### Telegram SDK, broker и отдельный сервис

Отклонены как преждевременные. Для пяти методов достаточно небольшого типизированного adapter над встроенным `fetch`, PostgreSQL уже обеспечивает очередь и координацию.

## Последствия и ограничения

- Бесплатная локальная разработка не требует публичного HTTPS или внешнего tunnel.
- Бизнес-транзакции не зависят от доступности Telegram.
- Несколько worker-процессов безопасно делят outbox; только один получает updates.
- Клиентская связь остаётся строго per-appointment, административные связи поддерживают несколько администраторов одной установки.
- База получает несколько целевых таблиц и ручные SQL constraints/partial indexes, но не универсальную event-bus платформу.
- Worker downtime свыше 24 часов может необратимо потерять Telegram updates согласно внешнему лимиту; пользователь восстанавливается новой deep link.
- Между последней проверкой и внешним `sendMessage` остаётся неизбежное окно: отмена, перенос или отзыв connection, победившие уже после начала HTTP-запроса, не могут отозвать сообщение.
- `SENT` означает полученный успешный ответ Bot API, а не доказательство прочтения пользователем.
- ADR остаётся Proposed до реализации и приёмки блоков 06.2–06.5.

Детальная модель, матрица, протоколы и порядок реализации описаны в [техническом плане этапа 06](../telegram-notifications-plan.md).
