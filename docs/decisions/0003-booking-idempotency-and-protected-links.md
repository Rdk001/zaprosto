# ADR-0003: Идемпотентное бронирование и постоянная защищённая ссылка

- Статус: Accepted
- Дата: 2026-08-30

## Контекст

Этап 04.1 добавляет серверное создание записи и отмену клиентом. Повтор после потерянного ответа должен возвращать ту же запись и ту же защищённую ссылку. В БД нельзя хранить открытый токен, а один идентификатор записи или ключ идемпотентности не должен давать доступ к подтверждению. Изменения каталога и последующая отмена не должны ломать распознавание исходного запроса.

## Решение

### Секрет попытки

До первого запроса вызывается серверный `prepareBookingAttempt()`: он создаёт случайный UUID ключа идемпотентности и независимый секрет из 32 криптографически случайных байтов (`randomBytes`, 256 бит, canonical base64url без padding). Генерация не обращается к БД и не создаёт запись.

Вызывающая сторона сохраняет пару **до** отправки `createBooking` и повторяет её без изменений при потере ответа. `cancellationToken` является секретом защищённой ссылки и предъявляется как доказательство права повторного получения подтверждения. Сервер сохраняет только SHA-256 токена в существующем `Appointment.cancellationTokenHash`; при повторе проверяет hash и возвращает предъявленный исходный токен, не создавая новый и не инвалидируя прежний.

Один ключ, ID записи или телефон не позволяют восстановить ссылку. При утрате секрета автоматического восстановления нет. Для новой попытки после успешного бронирования требуется новая пара. Срок запрета отмены и срок действия ссылки не вводятся.

В 04.2 потребуется реализовать сохранение пары в клиентском сценарии до отправки, доставку по HTTPS, защиту от XSS, исключение токена из аналитики и логов, `no-store`, политику referrer и подтверждение изменяющего запроса. Сейчас нет публичного обработчика или выбранного URL-маршрута; сервис возвращает токен для будущей защищённой ссылки.

### Отпечаток и совместимость

Новая миграция добавляет nullable `BookingRequest.requestHash` с проверкой формата SHA-256. Поле хранит hash канонического массива версии `booking-v1`: ID услуги, способ выбора мастера, исходный ID конкретного мастера или `null`, локальная дата, UTC-начало, нормализованные имя и телефон. Цена, длительность, окончание и назначенный при ANY мастер в отпечаток не входят: их выбирает сервер.

Отпечаток не вычисляется заново по изменяемой записи. Поэтому повтор исходного запроса работает после изменения каталога, ухода даты за горизонт и отмены; возвращается текущее состояние той же записи. Другие данные или другой токен с тем же ключом дают `IDEMPOTENCY_CONFLICT` без подтверждения. Повтор не добавляет историю и не восстанавливает отменённую запись.

Существующие строки остаются с `requestHash = NULL`. Они не получают выдуманного отпечатка и не допускаются к успешному повтору; уже существующие hashes защищённых ссылок не изменяются. Схема и старые миграции не переписываются.

### Транзакции и конфликты

Создание выполняется в PostgreSQL `Serializable`. Первый шаг — параметризованный `INSERT BookingRequest ... ON CONFLICT (idempotency_key) DO NOTHING`. Только этот уникальный ключ обозначает повтор. При параллельном запросе PostgreSQL ждёт конкурента; сериализационный конфликт приводит к повтору всей транзакции с новым снимком.

Для новой попытки scheduling получает именно транзакционный Prisma-клиент: выбирает ANY, повторно проверяет конкретного мастера, дату и окно. Снимки названия, цены, длительности и точное окончание берутся из того же актуального снимка БД. `BookingRequest`, `Appointment` (`SCHEDULED`, `ONLINE`) и начальная история (`CLIENT`) фиксируются атомарно. Неуспех проверки откатывает в том числе запрос, не оставляя незавершённую попытку.

Exclusion constraint `appointments_no_overlap` остаётся окончательной защитой для всех путей записи в БД. Фактически проверенная форма Prisma 7.10.0 / adapter-pg 7.10.0: `P2039`, вложенный `meta.driverAdapterError.cause.code = 23P01` и сообщение с точным именем этого ограничения. Адаптер не сохраняет отдельное поле `constraint` для этой ошибки, поэтому проверяется точное сообщение PostgreSQL. Остальные exclusions, `P2004`, `P2002`, ошибки инфраструктуры и конфигурации не маскируются под занятое окно.

После отката конфликт возвращает `SLOT_UNAVAILABLE` со свежей доступностью, прочитанной в отдельной `RepeatableRead`-транзакции. Если услуга/мастер к этому моменту недоступны или дата вышла за горизонт, результат содержит пустые окна и типизированную причину. Неизвестная ошибка остаётся ошибкой.

Повторы ограничены тремя попытками: `P2034` для сериализации/deadlock и фактически проверенный `P2010` для raw SQL с вложенными `cause.kind = TransactionWriteConflict` и `cause.originalCode = 40001` (также `40P01` для deadlock). Исчерпание попыток не выдаётся за конфликт окна. Внешних сетевых вызовов внутри транзакции нет; параметры ожидания подключения и выполнения ограничены 5 и 10 секундами соответственно.

### Подтверждение и отмена

Просмотр ищет запись только по hash секретного токена, не меняет БД и возвращает явно выбранный DTO без внутренних hashes, ключа запроса и задач уведомлений. Токен неверного формата или неизвестный токен не раскрывают данные записи.

Отмена требует `confirmed: true`. В транзакции `ReadCommitted` условный `UPDATE ... WHERE cancellation_token_hash = ... AND status = SCHEDULED` переводит запись в `CANCELLED`. Только изменивший строку запрос добавляет историю, инициатора `CLIENT`, время и необязательную причину. PostgreSQL повторно проверяет условие после ожидания конкурента. Повторная отмена возвращает сохранённый результат, не переписывает причину и не создаёт второй переход. Ошибка сохранения истории откатывает смену статуса. `COMPLETED` и `NO_SHOW` не меняются; исходные данные не удаляются.

## Последствия

- Не требуются новые платные сервисы, серверный ключ для восстановления токенов, шифрование токенов в БД или таблица с открытыми секретами.
- Контракт требует сохранить исходный секрет на вызывающей стороне до первого изменяющего запроса; это обязательная часть будущего UI.
- Добавлено только одно nullable поле, совместимое со старыми строками.
- Проверки гонок используют реальные прикладные сервисы и PostgreSQL; проверка формы ошибки привязана к текущему адаптеру и должна быть повторена при его обновлении или изменении локали сообщений PostgreSQL.
- UI, ограничение частоты публичных точек входа, защита HTTP-запросов и интеграция уведомлений остаются последующими задачами. Сервисы не создают фиктивных уведомлений.
