# ADR-0009: Версия настроек и согласованный контекст времени

- Статус: Accepted — этап 05.4 прошёл независимую проверку и принят пользователем
- Независимые результаты: 377 unit/integration и 85 E2E успешно
- Дата: 2026-08-31

## Контекст

Смена зоны не должна превращать ранее показанное клиенту время в другое без нового согласия. Сокращение горизонта ограничивает новые записи, но не просмотр, отмену или replay существующих. Две административные формы не должны терять чужое изменение, включая возврат значений A → B → A. Изменения расписания уже используют протокол ADR-0008, а условия услуги и восстановление — ADR-0003/0007.

## Решение

### Настройки и расписание

Новая миграция добавляет только BusinessSettings.version: INTEGER, default 0, CHECK >= 0. Существующие значения и данные не переписываются. Каждое успешное сохранение увеличивает счётчик, даже если значения совпадают. Переполнение откатывается; сброс версии запрещён.

Сохранение принимает строгий DTO: version, строковое целое bookingHorizonDays от 7 до 90, timezone до 100 символов, boolean confirmedTimezoneChange. Целевая строка всегда id=1; название, медиа, аккаунты и контакты не принимаются. Именованную зону проверяет существующий Temporal/scheduling; числовые смещения запрещены, сервер не ограничен российскими зонами.

Порядок ReadCommitted-транзакции: проверка текущей сессии → общий с каталогом/расписанием advisory lock (526008, 52) → FOR UPDATE singleton-строки → повторная проверка активной сессии после обоих ожиданий → строгая схема, версия и подтверждение → одно UPDATE двух параметров и увеличение версии. Несовпадение версии даёт CONFLICT без актуальной версии для автоматической подстановки. Смена timezone без подтверждения даёт CONFIRMATION_REQUIRED. Ответ успеха содержит только version/timezone/bookingHorizonDays из транзакции. Чтение — RepeatableRead с проверкой сессии, без записи и кеша. Неизвестный исход COMMIT не повторяется.

Контекст времени — SHA-256 JSON-массива фиксированного порядка ["business-time-v1", version, timezone, bookingHorizonDays]. Это публичный несекретный отпечаток, а не средство авторизации. Версия обнаруживает ABA, значения дополнительно обнаруживают прямое изменение зоны/горизонта без увеличения версии (но не такое же прямое ABA). Один общий счётчик выбран как минимальный консервативный протокол: изменение только горизонта также требует сверки старого расписания и повторного клиентского выбора.

Редактор расписания читает businessContext вместе с зоной и графиком в RepeatableRead; сохраняет исходный expectedBusinessContext рядом с Master.version. Все три операции 05.3 сверяют оба контекста под прежним общим замком. Отсутствующий контекст старого редактора тоже даёт конфликт. Новую версию или отпечаток под старый ввод сервер и UI не подставляют. При конфликте ввод остаётся в исходной вкладке для ручной сверки.

### Публичные чтения и создание

Каталог читает настройки, услуги и назначения в одной RepeatableRead-транзакции. Контекст включает version, contextHash, timeZone и даты. Горизонт вычисляется существующим getBookingDateContext: N локальных календарных дней, включая сегодня; никаких N × 24 часов.

GET доступности принимает необязательный expectedBusinessContext и в одной RepeatableRead-транзакции читает контекст и выполняет scheduling. Если предъявленный отпечаток отличается, отвечает BUSINESS_CONTEXT_CHANGED с актуальной зоной и датами, без старых окон. Обычные ответы и недоступный выбор также несут контекст. GET ничего не сохраняет. Старый GET без отпечатка допустим как чтение, но не разрешает создание.

Создание сохраняет Serializable и порядок ADR-0007:

1. INSERT BookingRequest либо проверка успешного replay по исходному hash и секрету.
2. Для новой попытки проверка показанных условий услуги.
3. FOR SHARE singleton-настроек до конца транзакции, чтение и сравнение expectedBusinessContext.
4. Scheduling, проверка текущего горизонта, точные snapshots и атомарное создание записи/истории.

Если настройки изменились после снимка Serializable, ожидание FOR SHARE не разрешает использовать старую строку: PostgreSQL возвращает сериализационный конфликт, существующий ограниченный retry начинает новую транзакцию. Если бронирование уже удерживает FOR SHARE, настройки ждут его завершения. Операции имеют допустимый последовательный порядок; смена настроек не переносит завершённое бронирование. Конфликт контекста бросает исключение и полностью откатывает новую попытку, затем читает актуальный контекст отдельной RepeatableRead-транзакцией. Неудача этого чтения остаётся UNAVAILABLE и сохраняет исходную пару.

### UI и восстановление

Перед отправкой UI сохраняет показанный expectedBusinessContext вместе с исходными данными, секретом и expectedServiceTerms. Новая подготовка ключа и фоновая доступность не заменяют их. BUSINESS_CONTEXT_CHANGED обновляет зону и даты, сбрасывает слот и подтверждение, сохраняет контакты, требует повторного выбора и явной кнопки «Подтвердить обновлённые условия». Запоздавшие ответы отбрасываются по поколению запроса, ключу выбора с contextHash и версии; начало создания также инвалидирует незавершённую доступность. Обновление контекста не отправляет create.

booking-v3 включает прежние поля booking-v1, затем expectedServiceTerms (или null) и expectedBusinessContext. Если нового поля нет, алгоритмы booking-v1/v2 остаются побитово прежними. Парсер сохраняет необязательность обоих отпечатков только для исторического replay. Новый запрос без контекста не создаётся; существующая попытка воспроизводится до проверки текущих условий и горизонта. Старые hashes не мигрируются и не пересчитываются по записям.

Ключ sessionStorage и TTL не меняются. Старые pending читаются и отправляются буквально, без обогащения новым контекстом. UNAVAILABLE, потеря сети, FORBIDDEN, RATE_LIMITED и IDEMPOTENCY_CONFLICT не считаются отказом; автоматического выбрасывания пары или новой попытки нет. Успех возвращает актуальную зону из снимка транзакции для отображения прежнего UTC-момента.

### Семантика времени

Настройки не изменяют UTC-моменты записей, снимки услуги, историю, статусы, токены или локальные часы/даты расписания. Меняется только трактовка сохранённых локальных графиков для будущих расчётов и отображение UTC-моментов в зоне бизнеса. Перед сменой зоны UI показывает старую и новую зоны и последствия; флажок сбрасывается при каждом изменении новой зоны. Это не автоматический перенос визитов.

Строгие DST-правила остаются: несуществующие/неоднозначные границы не сдвигаются, не округляются и не исправляются. Проблемный график после смены зоны требует явного исправления администратором или закрытия даты.

## Последствия и ограничения

Нет новых зависимостей, ролей, платных сервисов, уведомлений или ручного управления записями. Схема и данные изменяются только новой миграцией. Origin/CSRF, no-store, nonce-CSP и полная навигация сохранены.

Глобальный административный замок рассчитан на небольшой MVP; FOR SHARE позволяет параллельные бронирования и ненадолго задерживает редкие изменения настроек. Exclusion constraint остаётся окончательной защитой пересечений. Прямой SQL вне протокола версий не защищает ABA; операторские изменения требуют отдельной сверки. Отзыв сессии после финальной проверки не отменяет уже выполняющуюся операцию.

Административный черновик хранится в памяти страницы; навигация его теряет. При конфликте или неизвестном исходе сохранение блокируется и предлагается отдельная новая вкладка для проверки. Exactly-once для административных операций не заявляется.
