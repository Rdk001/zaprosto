# ADR-0002: Выбрать стек PostgreSQL и модульный Next.js-монолит

- Статус: Accepted
- Дата: 2026-08-27

## Контекст

«Запросто» должен оставаться понятным junior-разработчику, профессионально выглядеть в портфолио и допускать последующую адаптацию для российского малого бизнеса. Для разработки нельзя требовать платных сервисов, а production-инфраструктуру будущий заказчик выбирает и оплачивает отдельно.

Одна установка обслуживает один барбершоп и один филиал. Независимое масштабирование частей системы, публичный API для нескольких клиентов и многопользовательский SaaS в MVP не требуются. Поэтому отдельный backend и микросервисная архитектура добавили бы эксплуатационную сложность без подтверждённой пользы.

Критический инвариант системы — отсутствие пересекающихся активных записей одного мастера. Предварительная проверка свободного времени в приложении не защищает от двух одновременных запросов, поэтому окончательная гарантия должна находиться в базе данных.

## Решение

### Технологический стек

- Node.js 24 LTS.
- Next.js, React и TypeScript в строгом режиме.
- Tailwind CSS для интерфейса и Zod для проверки данных на серверных границах.
- PostgreSQL 17.
- Prisma ORM и Prisma Migrate.
- Vitest для модульных и интеграционных тестов, Playwright для end-to-end тестов.
- Docker Compose для локальной разработки.

`schema.prisma` и применяемые SQL-миграции вместе являются совокупным источником истины для структуры базы данных. Возможности PostgreSQL, которые Prisma Schema Language не выражает, фиксируются ручными SQL-миграциями. Команда `prisma db push` запрещена для production; изменения production-схемы выполняются только версионированными миграциями.

### Форма приложения

Система строится как модульный монолит на Next.js без отдельного backend-приложения. Серверные возможности Next.js обслуживают страницы, действия интерфейса и необходимые HTTP endpoints, а бизнес-правила располагаются в независимых серверных модулях и не зависят от React.

Обработчик фоновых уведомлений запускается отдельным процессом `worker`, но собирается из того же репозитория и Docker-образа, использует те же прикладные модули и базу данных. Worker является ролью процесса модульного монолита, а не микросервисом.

### Хранение данных и защита от пересечений

Запись хранит точные `starts_at` и `ends_at` как моменты времени с часовым поясом. Для каждого мастера PostgreSQL запрещает пересечение диапазонов записей в активном статусе с помощью exclusion constraint. Диапазон является полуоткрытым `[начало, конец)`, чтобы новая запись могла начаться ровно в момент окончания предыдущей.

Ограничение создаётся ручной SQL-миграцией с расширением `btree_gist` и выражением на основе `tstzrange(starts_at, ends_at, '[)')`. Predicate ограничения включает только статус `SCHEDULED`, поэтому отменённая запись сохраняется в истории, но больше не блокирует время.

Таблица поминутной занятости `appointment_occupancy` не создаётся. Она дублировала бы интервалы, усложняла транзакции и делала продолжительность записи зависимой от искусственной дискретизации.

Прикладной расчёт доступности используется для показа вариантов и повторной проверки бизнес-правил. Создание или перенос записи выполняется транзакционно, однако окончательную гарантию отсутствия пересечения обеспечивает PostgreSQL. Конфликт ограничения преобразуется в понятный ответ пользователю со свежим списком свободных интервалов, а не во внутреннюю ошибку сервера.

Для ограничения обязателен интеграционный конкурентный тест: два параллельных запроса на пересекающиеся интервалы одного мастера не могут создать две активные записи.

### Расписание и время

Регулярное расписание задаётся недельными рабочими интервалами и перерывами в локальном времени бизнеса. Датированное исключение полностью заменяет недельное расписание мастера на указанную локальную дату и представляет выходной либо собственный набор рабочих интервалов.

Начала, предлагаемые интерфейсом, генерируются с шагом 15 минут. Фактические интервалы записей хранятся точно и не округляются до этого шага. Моменты времени записей хранятся в UTC и отображаются в настраиваемом IANA-часовом поясе бизнеса.

### Развёртывание и файлы

Локальная среда запускается через Docker Compose и включает PostgreSQL, web-приложение, worker и постоянные volumes. Для изображений вводится абстракция файлового хранилища:

- при разработке используется локальный volume;
- в production используется постоянный volume либо S3-совместимое объектное хранилище, выбранное заказчиком.

Через админку загружаются логотип барбершопа и одна фотография каждого мастера. Приложение не зависит от конкретного облачного провайдера.

Для каждого барбершопа разворачиваются отдельный экземпляр приложения и отдельная база данных. Мультиарендность не добавляется. Production-инфраструктура является инфраструктурой заказчика и оплачивается им отдельно.

Демонстрационная среда может содержать только явно вымышленные персональные данные.

## Рассмотренные альтернативы

- YDB отклонена как менее распространённая для целевых заказчиков и сопровождения проекта и как создающая ненужную зависимость от специфичной модели хранения.
- Drizzle ORM признана рабочей альтернативой, но Prisma выбрана за более простой для junior-разработчика типовой процесс, сгенерированный клиент и удобство сопровождения. Exclusion constraint в обоих случаях требует ручного SQL.
- Отдельный backend отклонён до появления нескольких независимых клиентов API, отдельного масштабирования или других подтверждённых требований.
- `appointment_occupancy` отклонена как избыточное дублирование временных интервалов.

## Последствия

- Локальная разработка не зависит от платной инфраструктуры.
- Стек распространён, переносим и пригоден для передачи другому разработчику или заказчику.
- Критический инвариант двойного бронирования проверяется на уровне PostgreSQL.
- Часть схемы нельзя увидеть только в `schema.prisma`; ручные SQL-миграции и конкурентный интеграционный тест обязательны для безопасного сопровождения.
- Файловое хранилище и способ production-развёртывания можно заменить без изменения предметной логики.
- Один экземпляр на барбершоп упрощает изоляцию данных, но не предоставляет SaaS-мультиарендность, которая не входит в MVP.
