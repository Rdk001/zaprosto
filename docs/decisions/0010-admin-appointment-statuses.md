# ADR-0010: Журнал и конкурентное изменение статусов записей

- Статус: Accepted — результат 05.5 принят пользователем после исправления замечания независимой проверки
- Дата: 2026-08-31
- Принято: 2026-09-01

## Контекст

Администратору нужны история визитов и утверждённые переходы статусов без календарной библиотеки и новых продуктовых функций. Старые карточки не должны перезаписывать действия другого администратора, клиентскую отмену или контекст времени. updatedAt и сравнение одного статуса не обнаруживают все ABA.

## Решение

Новая миграция добавляет Appointment.version: INTEGER, default 0, CHECK >= 0, и индекс (starts_at, id). Старые миграции не меняются. Начальные версии существующих записей равны нулю; их время, snapshots, история и hashes не переписываются. Каждая успешная смена статуса увеличивает версию: административная операция и существующий условный UPDATE клиентской отмены. Повтор отмены ничего не увеличивает. Переполнение откатывает всю операцию; сброс счётчика запрещён. Будущие пути изменения Appointment обязаны соблюдать этот же протокол.

Административная ReadCommitted-транзакция:

1. Проверка активной серверной сессии и строгого DTO.
2. Общий с каталогом/расписанием/настройками advisory lock (526008, 52).
3. FOR SHARE singleton-настроек; затем FOR UPDATE конкретной записи.
4. Повторная проверка активной сессии после всех ожиданий.
5. Сравнение исходных Appointment.version и expectedBusinessContext из карточки с актуальными значениями. Контекст использует существующий ADR-0009: версия, зона и горизонт, включая ABA.
6. Проверка разрешённого перехода и явного подтверждения отмены. Для COMPLETED/NO_SHOW чтение PostgreSQL clock_timestamp() после блокировок и сравнение с startsAt; при наступившем начале, включая равенство, статус допустим.
7. UPDATE только статуса/версии и, для отмены, cancelledAt/cancelledBy/cancellationReason; INSERT истории с previousStatus/newStatus/changedAt/changedBy=ADMIN/changedByAdminId из проверенной сессии. Оба действия атомарны.

Настройки используют тот же порядок advisory → строка настроек. Бронирование держит FOR SHARE настроек, но не блокирует существующую запись; клиентская отмена блокирует только запись. Обратного порядка нет. Если клиент выиграл гонку, административная карточка получает CONFLICT. Если администратор установил результат, клиентская отмена возвращает STATUS_NOT_CANCELLABLE. После любой отмены повтор не меняет инициатора, причину, время и историю. Exclusion constraint по-прежнему освобождает интервал только при CANCELLED.

Нет автоматического повторения административной транзакции. Ошибка, в том числе неизвестный исход COMMIT, возвращает только UNAVAILABLE без версии или признака успеха. UI сохраняет причину в памяти, блокирует повтор и предлагает сверку в новой вкладке. Конфликт также не подставляет актуальную версию под старое намерение. После подтверждённого успеха полная навигация перечитывает карточку и историю с новым nonce.

## Чтения и безопасность

Журнал и карточка читаются в RepeatableRead: начальная авторизация, настройки, запись и история используют один согласованный снимок. После чтения boundary сначала дожидается завершения транзакции и освобождения её соединения. Только затем getActiveAdmin через основной клиент выполняет отдельное актуальное чтение сессии и аккаунта, вне прежнего снимка. Прочитанные данные остаются локальными до успешной финальной авторизации: отзыв/истечение сессии или отключение аккаунта возвращают UNAUTHORIZED без данных, ошибка запроса — UNAVAILABLE без данных и без повторения.

Финальная проверка не должна выполняться из callback открытой транзакции: при 10 одновременных чтениях и штатном пуле из 10 соединений все транзакции могут ждать дополнительное соединение из занятого ими же пула. Порядок «завершить транзакцию → проверить доступ → вернуть снимок» устраняет это ожидание; размер пула, maxWait и timeout не увеличиваются, обе проверки доступа сохранены. Регрессии журнала и карточки синхронизируют 10 реальных чтений, а сценарии отзыва/истечения/отключения отдельно проверяют отсутствие открытой транзакции перед финальной авторизацией и отсутствие контактов в отказе.

Исключения не логируются и превращаются в безопасный код. Отзыв уже после последней проверки не может отменить завершённую операцию или ранее выданные данные.

День определяется по startsAt в текущей зоне бизнеса; по умолчанию берётся сегодняшний локальный день по времени БД. Границы строит getLocalDayInterval, полуинтервал [начало, начало следующего календарного дня), без 24-часового предположения и без ограничения горизонтом. Невозможная/неоднозначная полночь даёт явную ошибку, а не сдвиг даты.

Сервер читает 25 записей или событий и ещё одну строку для признака следующей страницы. Журнал сортируется startsAt → id, история changedAt → id. Страницы — положительные целые до 9 999 999; offset ограничен этим форматом, размер страницы клиент не задаёт. Мастера читаются по 50 с UUID-курсором, плюс выбранный мастер вне текущей страницы. Деактивация мастера/услуги не скрывает историю. Параметры даты/мастера/статуса/страниц сохраняются в навигации; смена фильтра начинает журнал с первой страницы.

DTO чтения выбирает конкретные поля, без token hashes, sessions, Telegram/outbox, BookingRequest и связанной текущей услуги. Журнал показывает имя клиента, карточка — также телефон. Сведения об инициаторе истории — роль и сохранённый ID администратора, без чтения аккаунта. Ни контакты, ни причина не включаются в навигационные URL. Защищённая клиентская ссылка не генерируется: исходный секрет из hash не восстанавливается.

Mutation принимает только UUID, целую версию, SHA-256 контекст, enum статуса, boolean confirmed и необязательную причину до 1000 символов. Причина применяется только к отмене, пустая строка становится null. Origin/Sec-Fetch-Site, лимит Actions 16 КиБ, динамические страницы, private/no-store, nonce-CSP и полная навигация сохраняются. GET не изменяет данные.

## Совместимость и ограничения

booking-v1/v2/v3 replay не меняется: исходный payload/hash и секрет возвращают ту же запись с текущим статусом и зоной. Нет новой попытки, восстановления старого состояния или вращения ссылки.

Для небольшого MVP сохранён общий административный замок и простая offset-пагинация. Каждый новый GET видит свежий снимок; при одновременных вставках/отменах состав страниц может измениться, долговременный снимок всего журнала не обещается. Прямой SQL без увеличения версии не защищён от ABA. Неизвестный результат не означает отказ; отдельной административной exactly-once доставки нет, но тот же исходный DTO не может повторно изменить запись.

Контакты/причина в памяти вкладки теряются при её закрытии/навигации. Уже открытая страница не удаляет ранее выданные данные после отзыва сессии. Production HTTPS/proxy, другие браузеры, внешний аудит безопасности и прежние 3 high npm audit остаются отдельными вопросами. Платные сервисы, зависимости, ручное создание/перенос, Telegram/outbox и deployment не добавлены.
