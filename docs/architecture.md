# Архитектура

## Статус

Технологический стек и архитектура MVP утверждены в [ADR-0002](decisions/0002-choose-application-stack-and-architecture.md). Система строится как модульный монолит без отдельного backend и без зависимости от конкретного облачного провайдера.

## Контекст системы

«Запросто» — русскоязычная mobile-first система онлайн-записи для барбершопа. Клиент создаёт запись через публичный интерфейс, а администратор управляет данными бизнеса, расписанием и записями.

Одна установка обслуживает один барбершоп и один филиал. Для каждого покупателя разворачиваются отдельный экземпляр приложения и отдельная база данных. Мультифилиальность и многопользовательский SaaS не входят в MVP.

## Технологический стек

- Node.js 24 LTS.
- Next.js, React и TypeScript в строгом режиме.
- Tailwind CSS и Zod.
- PostgreSQL 17.
- Prisma ORM и Prisma Migrate.
- Vitest и Playwright.
- Docker Compose для локальной разработки.

`schema.prisma` и SQL-миграции вместе образуют совокупный источник истины для структуры базы. Невыразимые в Prisma Schema Language ограничения PostgreSQL создаются ручными SQL-миграциями. `prisma db push` запрещён для production; production-схема изменяется только версионированными миграциями.

## Топология приложения

Next.js является единым web-приложением и серверной точкой входа. Отдельный backend не создаётся.

- Server Components обращаются к прикладным сервисам напрямую, без HTTP-вызовов собственных Route Handlers.
- Server Actions обслуживают изменения из публичного интерфейса и админки.
- Route Handlers используются для внешних HTTP-сценариев: Telegram webhook, защищённые ссылки и технические endpoints.
- Бизнес-правила находятся в серверных модулях и не зависят от React или HTTP.
- Prisma используется только на серверной стороне.

Worker уведомлений запускается отдельным процессом того же приложения и Docker-образа. Он использует общие модули и PostgreSQL и не является микросервисом.

## Модули

Предусмотрены предметные модули:

- `catalog` — услуги, мастера, назначения услуг и порядок мастеров;
- `scheduling` — недельные интервалы, перерывы, датированные исключения и расчёт доступности;
- `booking` — создание записи, выбор «Любого мастера» и обработка конфликтов;
- `appointments` — изменение записи, отмена, перенос, статусы и история;
- `auth` — администратор и серверные сессии;
- `media` — загрузка, проверка и хранение логотипа и фотографий мастеров;
- `notifications` — Telegram, outbox и фоновые попытки отправки.

Границы модулей нужны для разделения ответственности, но не требуют универсального repository или отдельного слоя для каждой таблицы. Простые запросы не оборачиваются в абстракции без практической пользы.

## Модель данных

### Настройки и каталог

- `BusinessSettings`: название, IANA-часовой пояс, горизонт бронирования и ссылка на логотип.
- `Service`: название, цена, длительность, активность и порядок отображения.
- `Master`: имя, описание, активность, административный порядок и ссылка на одну фотографию.
- `MasterService`: назначение доступных услуг мастеру.
- `MediaObject`: ключ хранилища, MIME-тип, размер, размеры изображения, checksum и время загрузки.

Услуги и мастера после использования в записи деактивируются, а не удаляются. Запись сохраняет снимок названия, цены и длительности услуги, чтобы последующее изменение каталога не искажало историю.

### Расписание

- `WeeklyWorkInterval`: мастер, день недели, начало и конец рабочего интервала в локальном времени.
- `WeeklyBreakInterval`: мастер, день недели, начало и конец перерыва.
- `ScheduleException`: мастер, локальная дата и тип `DAY_OFF` либо `CUSTOM_HOURS`.
- `ExceptionWorkInterval`: рабочие интервалы для `CUSTOM_HOURS`.

На одну дату мастера допускается одно исключение. Оно полностью заменяет недельный график этого дня. Начала доступных окон генерируются с шагом 15 минут, но длительность услуги и занятый интервал сохраняются точно и не округляются.

### Записи

- `Appointment`: мастер, услуга, точные `starts_at` и `ends_at`, контактные данные клиента, статус, источник, способ выбора мастера, снимок услуги, уникальный идентификатор клиентского запроса и hash токена отмены.
- `AppointmentStatusHistory`: предыдущее и новое состояние, время, инициатор и необязательная причина.

Отдельная сущность клиента в MVP не создаётся: у клиента нет аккаунта, имя и нормализованный телефон принадлежат конкретной записи. Таблица поминутной занятости `appointment_occupancy` не создаётся.

### Администратор и уведомления

- `AdminUser`: login, hash пароля, активность и данные защитной блокировки входа.
- `AdminSession`: hash непрозрачного токена, срок действия и отзыв.
- `TelegramConnection` и `TelegramLinkToken`: добровольное подключение клиента по одноразовой защищённой ссылке.
- `NotificationOutbox`: тип уведомления, плановое время, состояние попыток и ключ дедупликации.

Пароль администратора хешируется Argon2id. Сессионные и одноразовые токены сохраняются только в виде hashes.

## Расчёт доступности

Для выбранной услуги и даты система:

1. Определяет мастеров, которым назначена услуга.
2. Берёт недельные рабочие интервалы либо полностью заменяющее их датированное исключение.
3. Вычитает перерывы и активные записи.
4. Генерирует возможные начала с шагом 15 минут в часовом поясе бизнеса.
5. Оставляет только интервалы, в которые услуга помещается целиком.

Для «Любого мастера» среди свободных кандидатов выбирается мастер с наименьшим количеством забронированных минут за выбранный день, затем с меньшим количеством записей и при полном равенстве — стоящий раньше в административном порядке.

Моменты записей хранятся в UTC с типом PostgreSQL `timestamptz` и отображаются в настраиваемом IANA-часовом поясе бизнеса, по умолчанию `Europe/Moscow`.

## Защита от двойного бронирования

Прикладная проверка доступности нужна для интерфейса и повторной проверки бизнес-правил, но не является окончательной гарантией. Создание и перенос выполняются в транзакции, а запрет пересечений обеспечивает PostgreSQL exclusion constraint для `master_id` и диапазона `tstzrange(starts_at, ends_at, '[)')`.

Ключевые свойства ограничения:

- полуоткрытый диапазон `[начало, конец)`;
- ручная SQL-миграция и расширение `btree_gist`;
- predicate только для активного статуса `SCHEDULED`;
- отменённые записи остаются в истории, но не блокируют время;
- ограничение применяется одинаково к онлайн-записи, ручной записи и переносу.

Конфликт ограничения преобразуется в понятное сообщение и сопровождается свежим набором свободных интервалов. Для гарантии обязателен интеграционный конкурентный тест с двумя параллельными попытками создать пересекающиеся активные записи одного мастера.

## Файлы и изображения

Модуль `media` зависит от интерфейса файлового хранилища, а не от конкретного провайдера.

- Локальная разработка использует постоянный Docker volume.
- Production использует постоянный volume либо S3-совместимое хранилище заказчика.
- Через админку загружаются логотип барбершопа и одна фотография каждого мастера.
- Сервер проверяет фактический формат, размер и размеры изображения, удаляет метаданные, перекодирует файл и назначает случайный ключ.

## Развёртывание

Локальный Docker Compose включает PostgreSQL, web-приложение, worker и постоянные volumes. Он не требует платных сервисов.

Production разворачивается на отдельно оплачиваемой инфраструктуре заказчика. Приложение поставляется как переносимые контейнеры, получает настройки через environment variables и не использует специфичные функции конкретного облака. Способ запуска PostgreSQL, файлового хранилища, TLS и резервного копирования выбирается в инфраструктуре заказчика.

Миграции выполняются отдельным release-шагом до запуска новой версии приложения. Резервное копирование должно охватывать PostgreSQL и загруженные изображения.

## Безопасность и персональные данные

- Все входные данные проверяются на сервере через Zod и предметные правила.
- Имя и телефон собираются только для записи; email не собирается.
- Телефон нормализуется к `+7XXXXXXXXXX`.
- Секреты передаются через environment variables и не хранятся в репозитории.
- Session cookies имеют `HttpOnly`, `Secure` и `SameSite`; изменяющие запросы проходят проверку источника и авторизации.
- Телефоны, session tokens и токены отмены не выводятся в прикладные логи.
- Публичное бронирование, вход администратора и проверка защищённых ссылок ограничиваются по частоте.
- Демонстрационная среда содержит только явно вымышленные персональные данные.

## Архитектурные ограничения

- Не добавлять отдельный backend, микросервисы, брокер сообщений, многопользовательский SaaS и мультифилиальность без нового подтверждённого требования и ADR.
- Не заменять exclusion constraint только предварительной проверкой доступности.
- Не вводить `appointment_occupancy`.
- Не привязывать предметную логику к Next.js, Prisma, Telegram или конкретному файловому провайдеру.
- Не подключать платную инфраструктуру за счёт проекта без отдельного решения пользователя.
