# Клиентская запись: этап 04.2

## Маршруты и сценарии

- `/`: активные услуги → подходящий активный мастер или «Любой мастер» → календарная дата и окно → имя/телефон → проверка → результат. Каталог читает Server Component напрямую. Название, цена, длительность и termsHash поступают из одного снимка услуги; создание сверяет показанные условия в транзакции BookingService.
- `GET /api/availability?serviceId=…&localDate=…[&masterId=…][&expectedBusinessContext=…]`: строгая проверка query и расчёт через scheduling. С 05.4 контекст настроек и окна читаются в одной RepeatableRead-транзакции; ответ содержит начала окон, зону и context (version/contextHash/timeZone/dates), без контактов и секретов. Несовпадение предъявленного контекста возвращает BUSINESS_CONTEXT_CHANGED с актуальными датами/зоной, без старых окон. Нет masterId — «Любой мастер».
- `/appointment#<token>`: публичная оболочка без данных записи. После загрузки браузер передаёт fragment в действие чтения, вызывающее ClientAppointmentService. Неверная ссылка не раскрывает данные.
- Server Actions: prepareAttemptAction, createBookingAction, lookupAppointmentAction, cancelBookingAction. Все считаются публичными недоверенными точками входа. Клиент не управляет ценой, длительностью, окончанием и статусом.

Все даты берутся из календаря бизнеса с его горизонтом; Intl форматирует моменты с явным timeZone. Браузер не рассчитывает доступность. Смена услуги сбрасывает мастера и слот, смена мастера/даты сбрасывает слот. AbortController, флаг актуальности и ключ выбора не позволяют старому ответу подменить окна.

Серверный конфликт снимает выбранный слот, возвращает к выбору времени и инициирует свежий запрос scheduling. Контакты остаются в памяти формы. Копирование защищённой ссылки имеет сообщения об успехе и ручной способ при недоступности Clipboard API.

Отмена требует открытия формы и отдельного флажка подтверждения. Причина необязательна (до 1000 символов). Повтор отмены не добавляет историю. COMPLETED и NO_SHOW не отменяются. GET, preview и prefetch не вызывают отмену. Самостоятельный перенос не добавлен.

Кнопка «К содержимому» доступна первой по Tab и активируется Enter или Space. Она переводит фокус на основной блок `main[tabindex=-1]` и прокручивает его в видимую область, не меняя URL. Это сохраняет секрет fragment на странице записи; на главной цель фокуса есть и при недоступном каталоге. Следующий Tab продолжает навигацию внутри основного содержимого.

## Повтор и хранение

Ключ sessionStorage: `zaprosto.booking.v1`. Перед первым create сервер выдаёт пару по ADR-0003, затем браузер сохраняет исходный payload и проверяет запись чтением. Если хранилище недоступно, create не отправляется.

- Пока ответ неизвестен, редактирование и новая попытка заблокированы. Повтор сохраняет первоначальные имя, телефон, услугу, выбор мастера, дату, время, ключ, секрет и отпечатки expectedServiceTerms/expectedBusinessContext (только если соответствующие поля были в исходном запросе). Reload показывает отдельную панель продолжения.
- UNAVAILABLE, сетевой сбой, ограничение частоты и конфликт идемпотентности не считаются доказанным отказом исходной попытки. Доступны тот же повтор и защищённая ссылка.
- BUSINESS_CONTEXT_CHANGED, SERVICE_TERMS_CHANGED, SLOT_UNAVAILABLE, REQUEST_REJECTED, INVALID_INPUT — подтверждённые доменные отказы текущего неизменного запроса; сохранённая пара удаляется. Следующая отправка получает новую пару.
- При успехе payload заменяется маркером receipt с одним токеном. Контактов в sessionStorage больше нет.
- Через 30 минут pending преобразуется в expired без контактов. Проверка выполняется при загрузке, pageshow и каждые 15 секунд, когда вкладка активна. В приостановленной вкладке очистка произойдёт при возобновлении; браузерное хранилище не умеет удаляться само по часам, когда приложение не исполняется.
- Просроченное или повреждённое состояние не исчезает незаметно. Пользователь сначала проверяет результат, затем может явно подтвердить начало заново с предупреждением о риске второй записи.
- Новая запись после успеха очищает маркер и контакты формы. Закрытие вкладки обычно удаляет sessionStorage, но восстановление сессии браузером может его сохранить. Сам токен не имеет срока отмены, как требует ADR-0003. Автоматического восстановления утраченного токена нет.

Нельзя гарантировать восстановление после очистки хранилища самим пользователем/браузером. Хранилище доступно скриптам того же origin; сторонние скрипты и аналитика на этих страницах запрещены.

## Изменение настроек времени (05.4)

Публичный каталог передаёт context с отпечатком версии/зоны/горизонта из согласованной транзакции. Новый create сохраняет expectedBusinessContext вместе с исходной парой до отправки. Сервер после проверки replay сверяет контекст в транзакции; старые booking-v1/v2 остаются восстанавливаемыми без добавления новых полей.

При BUSINESS_CONTEXT_CHANGED UI обновляет зону, даты и окна, сбрасывает слот и подтверждение, сохраняет контакты и требует явного повторного выбора/кнопки «Подтвердить обновлённые условия». Запоздавшая доступность отбрасывается по поколению запроса, ключу с contextHash и версии. Начало create инвалидирует фоновые ответы; они не меняют исходную сохранённую попытку. Сокращение горизонта проверяется на сервере. Неизвестный исход сохраняет прежнюю пару и блокирует автоматическое новое создание. См. [ADR-0009](decisions/0009-business-time-context.md).

## Изменение услуги перед подтверждением

SERVICE_TERMS_CHANGED обновляет название, цену и длительность в основном блоке формы, включая мобильный экран; время сбрасывается, доступность запрашивается заново. Контакты сохранены. Перед новой отправкой нужны выбор окна, просмотр всех условий и явная кнопка «Подтвердить обновлённые условия». Отпечаток меняется вместе с показанными условиями только после подтверждённого отказа; запрос доступности, reload незавершённой попытки и prepare не подставляют его автоматически.

Старый pending без expectedServiceTerms остаётся исходным запросом: повтор либо получает уже созданную booking-v1, либо отказ новой попытке без согласованных условий. Для booking-v2 удаление поля даёт конфликт исходного requestHash и сохраняет блокировку. Несовместимый или повреждённый формат не разрешает автоматическое начало заново. См. [контракт](booking-service.md) и [ADR-0007](decisions/0007-booking-service-terms.md).

## Защита и лимиты

PUBLIC_ORIGIN обязателен: точный внешний origin без завершающего slash, например `https://booking.example`. Отсутствующий Origin, `null`, другой origin и несовместимый Sec-Fetch-Site отклоняются до прикладного сервиса. Нельзя расширять allowedOrigins маской ради обхода проблем proxy.

Счётчики PostgreSQL имеют минутное окно с первого запроса. Используется время БД, атомарное увеличение с насыщением и транзакция; процессы не полагаются на локальную память.

| Операция           | На клиента в минуту | На установку в минуту |
| ------------------ | ------------------: | --------------------: |
| Подготовка попытки |                  20 |                   200 |
| Создание и повтор  |                  12 |                   120 |
| Проверка ссылки    |                  60 |                   600 |
| Отмена             |                  20 |                   200 |
| Доступность        |                 120 |                  1200 |

Просроченные счётчики удаляются при следующем обращении; при отсутствии трафика остаются до следующего запроса (без контактов и токенов). GET при лимите возвращает 429 и Retry-After: 60. Actions возвращают RATE_LIMITED. При недоступной БД операции не пропускаются: UNAVAILABLE, без внутренних подробностей.

TRUST_PROXY_CLIENT_IP=false — безопасный общий bucket для всех посетителей. Для production с индивидуальными лимитами:

1. Разместить приложение за доверенным reverse proxy и TLS.
2. Закрыть прямой доступ к порту Next.js сетевыми правилами; только proxy может обращаться к нему.
3. Proxy должен **перезаписывать**, а не дописывать X-Zaprosto-Client-IP адресом непосредственного проверенного клиента (для цепочки CDN сначала отдельно настроить доверенные адреса CDN). Пример для одного Nginx: `proxy_set_header X-Zaprosto-Client-IP $remote_addr;`.
4. Передавать корректные Host/X-Forwarded-Host, соответствующие PUBLIC_ORIGIN; приложение само не доверяет им для проверки источника.
5. Только после этого установить TRUST_PROXY_CLIENT_IP=true. Валидация принимает один IPv4/IPv6, не список. IPv6 приводится к каноническому виду.
6. Настроить ограничения размера тела и трафика на proxy. Next Actions дополнительно ограничены 16 KB.

Неправильная настройка доверия IP делает клиентский лимит обходным, хотя глобальный остаётся. Hash IP не означает полную анонимность: доступ к таблице должен быть ограничен.

## Кеширование, CSP и журналирование

Страницы и endpoint доступны только с private/no-store, no-referrer, noindex/nofollow/noarchive; персональные ответы не кешируются CDN. Скрипты разрешены nonce-CSP, без unsafe-inline и unsafe-eval в production. Inline styles разрешены для совместимости Next.js; внешние шрифты, картинки, трекеры и embed не используются. Фреймы запрещены. Все поля выводятся экранированным React-текстом. В dev unsafe-eval нужен Next.js.

Секрет находится во fragment, который HTTP не передаёт; он всё ещё виден в адресной строке, истории браузера и при ручной передаче ссылки. Не делать query/path-алиасы с токеном и не сохранять полный browser URL в события аналитики. Если пользователь ошибочно вставил токен в query, access logs могут захватить его: proxy должен журналировать путь без query либо редактировать параметры до хранения. Для этих маршрутов отключить запись тел POST, Flight-ответов, request dumps, APM payload, console breadcrumbs, HAR и session replay. Reverse proxy, CDN и error tracker требуют отдельной настройки — приложение не может стереть уже сохранённые внешние логи.

В прикладной границе исключения не логируются: Prisma может включить персональные параметры в текст ошибки. Клиент получает только безопасный код. Для мониторинга использовать агрегированные счётчики кодов без request/response bodies и URL fragment. Playwright traces отключены; тестовые снимки содержат только вымышленные данные.

Production использует HTTPS и HSTS на proxy. При нескольких процессах использовать одну сборку и общий NEXT_SERVER_ACTIONS_ENCRYPTION_KEY согласно локальной документации Next.js. Секрет ключа задаётся вне репозитория.

## Локальная демонстрация

Требуются Node.js 24 и PostgreSQL 17. Миграции не сбрасывают существующие данные.

```bash
cp .env.example .env
docker compose up -d db
npm install
npm run prisma:migrate:deploy
npm run demo:seed
npm run dev
```

Открыть http://localhost:3000. PUBLIC_ORIGIN в .env должен совпадать с адресом браузера. Если порт 3000 занят прежним Docker web, остановить только этот контейнер либо выбрать другой порт и изменить PUBLIC_ORIGIN соответственно.

demo:seed запускается только вручную. Команда добавляет три явно вымышленные услуги, двух мастеров, недельный график 10:00–20:00 и перерыв 14:00–15:00. Использует зарезервированные UUID, не очищает таблицы, не перезаписывает существующие настройки и строки демокаталога, не создаёт записей и клиентских контактов. Повторный запуск ничего не дублирует. Не запускать на реальном каталоге без намерения добавить демоуслуги.

## Проверки

```bash
npm run format:check
npm run lint
npm run build
npm run typecheck
npm run test:postgres
npm run test:e2e
```

test:postgres запускает все Vitest-тесты на созданной им случайной БД; test:e2e тоже создаёт отдельную БД, применяет миграции и заполняет демокаталог. Нужны права CREATE DATABASE. Исходная БД не изменяется, временная удаляется в finally. Без .env можно запускать `node --env-file=.env.example scripts/test-postgres.mjs [--e2e]`.

E2E использует production build (предварительно npm run build), Chromium и порт 3108, никогда не переиспользует чужой сервер. Успешные операции идут через настоящие Actions и PostgreSQL. Route interception применяется для потери ответа, задержек и проверки неполных/подменённых запросов; успешные ответы создания не имитируются. Снимки адаптивных страниц сохраняются в test-results; секреты не должны попадать в публикуемые отчёты.

## Граница

Админка, клиентская авторизация, платежи, SMS, переносы, Telegram и отправка уведомлений не реализованы. Telegram остаётся этапом 06; UI не показывает кнопку подключения и не обещает доставку. Полная production-конфигурация proxy, TLS, резервного копирования и эксплуатации требует проверки на инфраструктуре заказчика.
