# Настройки времени и горизонта бронирования (05.4)

## Открытие и обновление установки

Войдите существующим администратором через /admin/login и откройте «Настройки» (/admin/settings). Страница читает сохранённые значения и ничего не сбрасывает. Для новой установки остаются Europe/Moscow и 30 дней. Создание аккаунта — только по [прежней инструкции](admin-auth.md).

Этап добавляет миграцию 20260831200000_settings_version. Перед обновлением реальной установки оператор делает резервную копию и применяет её штатным prisma:migrate:deploy, затем запускает актуальную сборку. В рамках проверки задачи миграции применяются только runner к случайным тестовым БД. Не используйте db push, reset, редактирование старых миграций или сброс существующих настроек.

## Сохранение

- Горизонт: целое число от 7 до 90 без дробей, знаков и пробелов. Это локальные календарные дни бизнеса, включая сегодня: 7 означает сегодня и следующие шесть дат.
- Зона: именованный IANA timezone, например Europe/Moscow, Asia/Yekaterinburg, Europe/Berlin, America/New_York. Сервер использует ту же проверку Temporal, что расписание. Произвольные смещения вроде +03:00 не принимаются.
- Изменения полей ничего не сохраняют. Нажмите «Сохранить настройки»: оба значения сохраняются атомарно.
- При ошибке ввод остаётся. Сообщение успеха означает подтверждённое завершение сохранения; во время ожидания поля заблокированы.

Название, логотип, фотографии, Telegram и другие настройки в этот экран не входят.

## Смена зоны

Перед сохранением показаны старая и новая зоны и обязательный флажок понимания последствий. При изменении новой зоны флажок сбрасывается. Сервер также проверяет подтверждение.

Существующие UTC-моменты визитов не меняются, но в новой зоне могут показываться в другой час или день. Это **не автоматический перенос визитов**. Снимки услуги, статусы, история и защищённые ссылки остаются прежними.

Недельные локальные часы и даты исключений не пересчитываются. Будущая доступность трактует их в новой зоне; после смены проверьте [графики и исключения](admin-schedule.md). Несуществующие или неоднозначные времена DST не исправляются автоматически: задайте корректные границы или выходной для проблемной даты.

Сокращение горизонта ограничивает новые записи. Старые записи за пределами нового горизонта не отменяются; их можно просматривать, отменять и восстанавливать по прежней попытке.

## Старые вкладки и потеря связи

Каждое сохранение увеличивает версию, даже если повторены те же значения. Две формы с одной версией не могут молча перезаписать друг друга, в том числе после A → B → A. При конфликте кнопка блокируется, черновик остаётся в исходной вкладке. Нажмите «Проверить актуальные настройки (новая вкладка)», сравните значения и только затем перенесите нужный ввод в свежую форму.

При «Сохранение не подтверждено» сервер мог успеть сохранить запрос. Успех не показан, автоматического повтора нет. Не отправляйте повтор из другой вкладки до проверки актуальных данных. Ошибка/конфликт не заменяет версию в исходном черновике. Навигация или закрытие страницы теряет несохранённый ввод.

Старый редактор расписания после изменения настроек тоже получает конфликт без изменения введённых часов. Откройте актуальный график отдельно и сверьте зону. Консервативно это относится также к изменению только горизонта.

Открытая клиентская форма при изменении настроек обновляет зону, даты и окна, сохраняет имя/телефон и требует заново выбрать время и подтвердить условия. Новое создание проверяет контекст на сервере. Уже успешная попытка, включая booking-v1/v2, восстанавливает прежнюю запись. При неизвестном исходе клиент должен повторить именно исходный запрос или проверить защищённую ссылку, а не создавать новую пару.

## Безопасность и проверки

Каждое административное чтение и изменение проверяет активную сессию. После ожидания административного и строкового замков доступ проверяется повторно. GET ничего не сохраняет; Origin/CSRF, no-store, nonce-CSP и полная навигация сохранены. DTO не содержит контактов и секретов.

Проверки выполняйте только штатным runner на случайной отдельной PostgreSQL-БД:

```bash
npm run format:check
npm run lint
npm run build
npm run typecheck
node --env-file=.env.example scripts/test-postgres.mjs
node --env-file=.env.example scripts/test-postgres.mjs --e2e
git diff --check
```

Для собственной локальной конфигурации используйте npm run test:postgres / test:e2e. Build/Prisma generate должны закончиться до typecheck. Runner удаляет только созданную им временную БД; рабочие базы, аккаунты и volumes не очищаются. Протокол — [ADR-0009](decisions/0009-business-time-context.md), результаты и пределы проверки — [progress.md](progress.md). Вопрос npm audit из 05.1 сохраняется; обновления зависимостей и audit fix сюда не входят.
