# Серверное бронирование: этап 04.1

Эта страница описывает независимые прикладные сервисы этапа 04.1. Подключённый UI, HTTP endpoint доступности и Server Actions этапа 04.2 описаны в [public-booking.md](public-booking.md). Для Next.js следует импортировать `booking` и `prepareBookingAttempt` из `src/modules/booking/server`, а `clientAppointments` — из `src/modules/appointments/server`: эти точки входа помечены `server-only`. Factory-функции в файлах сервисов предназначены для серверной композиции и тестов.

## Контракт вызовов

```ts
// Выдать и сохранить пару ДО отправки запроса на создание.
const attempt = prepareBookingAttempt();

const result = await booking.createBooking({
  ...attempt,
  serviceId,
  master: { type: "SPECIFIC", masterId }, // либо { type: "ANY" }
  localDate: "2026-10-05", // календарная дата в часовом поясе бизнеса
  startsAt: "2026-10-05T10:00:00+03:00", // ISO с offset либо валидный Date
  clientName: "Вымышленный Клиент",
  clientPhone: "8 (999) 000-00-00",
});

// Тот же объект с той же парой безопасно отправляется повторно при потере ответа.
// При успехе result содержит confirmation, cancellationToken и replayed.
const confirmation = await clientAppointments.getConfirmation(attempt.cancellationToken);

// Выполняется только после явного подтверждения пользователем; чтение не отменяет.
const cancellation = await clientAppointments.cancelBooking({
  token: attempt.cancellationToken,
  confirmed: true,
  reason: "Изменились планы", // необязательно
});
```

Все параметры сервисов принимаются как `unknown` и проверяются на серверной границе. Неизвестные поля отклоняются: клиент не передаёт цену, окончание, длительность, статус, источник, снимки или `excludeAppointmentId`. Имя обрезается по краям и должно содержать 1–200 символов; телефон проверяется существующим валидатором и сохраняется в `+7XXXXXXXXXX`. Технические пределы ввода: телефон 64 символа, причина отмены 1000. Пустая причина хранится как `null`.

Успешный DTO содержит ID и текущее состояние записи, назначенного мастера, снимок услуги, UTC-начало и окончание, контактные данные и сведения об отмене. Интерфейс должен отображать UTC-моменты в настроенном часовом поясе бизнеса. В DTO нет hashes и ключа идемпотентности. Токен возвращается отдельно только при создании/подтверждённом повторе; он и контакты не должны попадать в логи, аналитику или публичный кеш.

## Ожидаемые результаты

| Операция               | Код                      | Значение                                                                                         |
| ---------------------- | ------------------------ | ------------------------------------------------------------------------------------------------ |
| Создание               | `INVALID_INPUT`          | Некорректные поля; `issues` содержит только имена полей и сообщения                              |
| Создание               | `REQUEST_REJECTED`       | Услуга отсутствует/неактивна, мастер не подходит или дата вне горизонта                          |
| Создание               | `SLOT_UNAVAILABLE`       | Окно недоступно; `availability` содержит свежие окна или причину недоступности                   |
| Создание               | `IDEMPOTENCY_CONFLICT`   | Ключ уже связан с другой попыткой, данные/секрет не совпадают либо у старой строки нет отпечатка |
| Подтверждение / отмена | `NOT_FOUND`              | Неизвестная защищённая ссылка; данные записи не возвращаются                                     |
| Отмена                 | `INVALID_INPUT`          | Не подтверждена отмена или некорректен формат запроса                                            |
| Отмена                 | `STATUS_NOT_CANCELLABLE` | Клиент не может отменить `COMPLETED` или `NO_SHOW`                                               |

Неожиданные ошибки БД и конфигурации пробрасываются. Будущий HTTP-слой должен безопасно обрабатывать их без отправки stack trace, Prisma invocation, телефонов и токенов клиенту или в логи. Три неудачные попытки сериализации не означают, что выбранное окно занято.

## Проверки

`npm test` запускает unit- и PostgreSQL integration-тесты; для integration необходима мигрированная тестовая БД в `TEST_DATABASE_URL` или `DATABASE_URL`. Не следует направлять этот набор на рабочую БД: существующие тесты scheduling временно меняют singleton-настройки.

Для изоляции добавлен `scripts/test-postgres.mjs`: он создаёт случайную отдельную БД, применяет все миграции, запускает весь набор Vitest и удаляет только созданную им БД в `finally`. Исходная БД из URL не мигрируется и не очищается. Роль тестового PostgreSQL должна иметь право `CREATE DATABASE`.

Для стандартного локального Docker Compose из репозитория:

```bash
node --env-file=.env.example scripts/test-postgres.mjs
```

При собственном `.env`:

```bash
npm run test:postgres
```

Аргументы Vitest можно передать после `--`, например `npm run test:postgres -- --project integration`. Тесты используют вымышленные контакты и очищают только собственные fixture-записи. Новая миграция — `20260830120000_add_booking_request_hash`; старые миграции не менялись.

Подробности безопасности, совместимости и транзакций: [ADR-0003](decisions/0003-booking-idempotency-and-protected-links.md).

## Граница этапа

04.1 не включает интерфейс записи, админку, авторизацию, перенос, Telegram-бота или отправку уведомлений. В 04.2 сервисы подключены к русскоязычному mobile-first UI; публичные точки входа защищены проверкой Origin и ограничением частоты в PostgreSQL. Telegram остаётся этапом 06.
