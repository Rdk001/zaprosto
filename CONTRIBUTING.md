# Участие в разработке

## Рабочий процесс

1. Создайте отдельную ветку от актуальной основной ветки.
2. Делайте небольшие, логически завершённые коммиты.
3. Обновляйте документацию и `CHANGELOG.md`, если меняется поведение продукта.
4. Перед отправкой изменений запускайте доступные проверки форматирования, тесты и сборку.
5. В описании изменений укажите цель, способ проверки и известные ограничения.

## Ветки и коммиты

Рекомендуемые префиксы веток: `feat/`, `fix/`, `docs/`, `chore/`.

Сообщение коммита должно кратко описывать результат в повелительном наклонении. Допустим формат Conventional Commits, например:

```text
docs: add project bootstrap documentation
```

## Качество

- Не добавляйте секреты, ключи и локальные файлы окружения.
- Новое поведение должно сопровождаться тестами, когда тестирование применимо.
- Публичные интерфейсы и нетривиальные решения должны быть документированы.
- Значимые архитектурные решения оформляйте отдельным ADR в `docs/decisions/`.

## Definition of Done

Изменение считается готовым, когда оно реализовано, проверено, документировано и не оставляет известных ошибок в затронутом сценарии.
